# Sidecar FP8 user setup and support status — 1.3.3-rc1

**This is a documentation update for an internal-only candidate. No executable or release archive is attached or cleared for redistribution.** The candidate was exercised offline only; it was not installed, connected to a pool, or run on a GPU.

## Installation and host requirements

The current build targets Linux x86-64 with Python 3.12 in a private environment. Its native search binary depends on `libcudart.so.12` even when configured for CPU mode; CUDA/NVIDIA libraries are not bundled. The project helper can create a package-local virtual environment and install the pinned direct Python requirements, but the transitive SBOM and redistribution rights are not complete. Review the package scripts before use. Do not copy CUDA libraries from another miner.

Ubuntu receives read-only host preflight coverage only. HiveOS and RabidOS are detected but their package installation, service management, drivers, and rollback remain unverified.

## User workflow in the internal candidate

- The interactive wizard defaults to ABI 1 and CPU. It collects ordered primary/failover TLS pool endpoints, a wallet/account string, worker name, optional password environment-variable names, and a memory profile.
- Wallet input is hidden. Password values are not stored in the config. URL userinfo, query credentials, fragments, plaintext schemes, invalid pool counts, and overwriting an existing profile are refused.
- Read-only GPU UUID/PCI/model/VRAM discovery runs only after explicit opt-in to an `nvidia-smi` metadata query. It does not launch CUDA. ABI 2 is held to CPU because its exact worker receipt says `CPU_ABI_PASS_CUDA_NOT_RUN`; ABI 1 CUDA profile creation requires an explicit unqualified-canary acknowledgement.
- The JSON-backed terminal view displays only fields the runtime supplies. Missing GPU temperature, power, job age, reconnect, or public-share measurements are shown as unavailable. Local acknowledgments are distinct from pool responses; no local receipt implies a public share or accepted block.
- Release staging is dry-run by default. The user-local version manager checks archive/source hashes, refuses archive links and unlisted payloads, and keeps `current` and `previous` pointers for rollback. It rejects root/system prefixes and does not install or enable the example service. Updating means staging a new immutable version; uninstall requires an inactive version and preserves user configuration.
- Foreground stop is Ctrl-C/SIGTERM. The example systemd unit is disabled, has no `[Install]` section, and is never enabled by the package.

A paired MIDDLE UDS integration issue remains: the stock Gateway job mapping omits `job_id`, while the UDS envelope requires it. An isolated overlay has shown that exporting the matching active template ID and rejecting wrong IDs fixes that field boundary. It is not applied to the frozen runtime. Final candidate-correlated peer outcome handling is still unwired.

## Offline evidence and release restrictions

The internal candidate passed 51/51 focused offline package, configuration, lifecycle, archive, and rollback tests. An actual archive clean extraction, exact source-lock verification, and no-write install dry-run passed. No CUDA, GPU query, pool connection, service activation, production install, or payout change occurred.

External redistribution remains blocked pending a target-specific transitive SBOM and notices, written rights for the packaged native binaries, and a supported OS/driver/runtime matrix. The current evidence identifies license and provenance gaps; it does not establish that any named component is incompatible.
