# Project Sidecar

## Miner software release candidate (0.3.0-rc1)

The isolated `sidecar-miner` software release candidate brings together PRL job/share handling, the offline-first supervisor and one-share canary guard, backend qualification artifact handling, an FK33 fleet lifecycle model, and first-silicon timing/scaling analysis. The miner supports GPU/FK/auto policy interfaces and mock-only offline execution; its presence does not qualify either real backend.

**Real CUDA PearlHash backend qualification: pending. PHK1 physical RAW_BSCAN qualification: pending.** Both are deliberately fail-closed in this release candidate. No live Kryptex operation is enabled. The patched PHK1 candidate has passed offline simulation, synthesis, implementation, timing, and DRC checks according to the project status. Bitstream generation is currently blocked because the available Vivado license does not enable `write_bitstream` for the VU33P target. That licensing work is separate from this software release.

After a valid first-silicon result, the planned sequence is: ingest measured timing, compare end-to-end performance, and consider the guarded 1 → 2 → 4 → 8 FK rollout only after qualification, correctness, health, and rollback gates pass. See [miner release notes](CHANGELOG.md), [first-silicon workflow](docs/first-silicon-benchmark.md), and [fleet orchestration](docs/fleet-orchestration.md).

GPU + FPGA cooperative compute research for PearlHash/PRL using NVIDIA RTX GPUs and SQRL FK33 accelerators.

## Goal

Project Sidecar tests whether an FK33 pod can accelerate selected PearlHash stages alongside a GPU instead of operating only as independent miners. A sidecar is a win only if end-to-end throughput improves after transfer, synchronization, scheduling, FPGA processing, and return-path overhead are included.

## Immediate next milestone

Keep the newly installed production Sidecar on a stable, read-only observability path while returning engineering effort to the project’s core acceleration goal: qualify the next safe GPU↔FK33 data-path step, measure transport/runtime overhead, and determine whether real end-to-end throughput improves.

The production deployment is now a known-good baseline and should not be redesigned as part of ordinary acceleration experiments. Hardware execution remains separately gated and requires explicit authorization.

See [initial production deployment milestone](docs/production-deployment-milestone.md) for the public-safe deployment checkpoint.

## Safety

Bring-up is fail-closed with authenticated releases, fixed hardware identity, independent recovery supervisors, bounded job renewal, authenticated rollback, and a retained BSCAN/JTAG recovery path. Public submission stays disabled during transport and sidecar qualification.
