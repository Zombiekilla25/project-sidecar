# CUDA backend status

The upstream qualified CUDA source and `libp40cuda.so` were found at the path recorded in [the source inventory](cuda-pearlhash-source-inventory.md). A source copy now lives under `third_party/pearlhash-cuda-src/`; only this isolated copy is patched/built. The old upstream artifact had a `DT_NEEDED` entry for `campaign/U8.so` because its CUDA object expected four symbols that the dependency provided. Those symbols have implementations in the qualified source tree and the documented build recipe links the defining sources directly.

## Build and runtime

The torch-free build is reproducible with `cd third_party/pearlhash-cuda-src && GENCODE='-gencode arch=compute_86,code=sm_86' bash packaging/build_capi.sh`. It uses CUDA 12 `nvcc` and the copied CUTLASS/CuTe headers, compiles for the local RTX 3080 architecture, and does not initialize CUDA or execute kernels. The compile/link result is `third_party/pearlhash-cuda-src/libp40cuda.so`.

The C API's `p40_pearl_pow_split` accepts already prepared device matrices and writes digest/found/coordinate buffers. A real Sidecar backend also needs to bridge the upstream matrix generation, commitment/noise preparation, bounded search and proof construction into a `BackendResult(Candidate)` with current job fingerprint/generation/batch identity. Reusing `miner_capi.mine_job` directly is unsuitable: it owns a continuous miner loop and its pool/proof worker lifecycle.

## Selection and safety

Sidecar config and CLI accept `SIDECAR_GPU_ID` / `--gpu-id`. The isolated C API adds explicit `p40_select_device` plus opaque `sidecar_cuda_create/destroy`, allocator/copy, prepare, batch, and sync operations. It queries the current selected device for architecture dispatch. Importing `sidecar_miner.cuda_backend` does not load a library; initialization is explicit and refuses the unqualified backend by default. Kernel output is currently raw digest/found/coordinate data and deliberately remains ineligible for submission until proof construction and the CPU oracle are wired to this path.

## Qualification status

No GPU kernel was executed and no CUDA timing was measured. The CPU-only existing operand fixture is not compatible as a CUDA raw digest oracle. The plan-only harness validates vector schema and makes no library load; its runtime command is bounded to one 16×16 tile, one launch, zero retries, timeout, one explicit device and no pool. `sidecar_miner.cuda_backend` is exported behind the existing backend module but real CUDA stays disabled by default. Full GPU-produced proof creation and CPU-oracle integration remain unqualified.

## CPU-qualified raw-digest fixture

The earlier `operand-vector-001` fixture cannot serve as a CUDA expected-output vector: it is a CPU-only operand/FPGA vector and does not describe the CUDA kernel's raw digest output contract. The CUDA implementation hashes one transcript for each logical tile containing 16 matrix rows × 16 matrix columns; these are matrix dimensions, not GPU warp lanes. Ampere requires matrix dimensions aligned to 64, so the minimum A[64,64] and Bt[64,64] shape produces 16 digest outputs.

`fixtures/cuda/pearlhash-16x16-raw-digest-v1.json` and its binary companions define signed-int8 C-row-major A/Bt inputs, key and target, plus 16 consecutive 32-byte raw keyed-BLAKE3 digest outputs in tile-row/tile-column order. Raw digest bytes are the BLAKE3 output sequence; the 16-word transcript is serialized little-endian before hashing. It is not a PHK1 raw/canonical result, nor a complete proof/share candidate.

Expected bytes are generated by the existing qualified upstream CPU `verify_tile` reference semantics (source identity and source hash are in the manifest), then replayed in independent processes. The validator re-creates deterministic matrices/key/target, checks hashes and exact CPU outputs. The self-test plan-only command accepts this fixture and mock comparisons test exact match, bit corruption and ordering errors. No CUDA library was loaded and no GPU execution occurred during fixture qualification.
