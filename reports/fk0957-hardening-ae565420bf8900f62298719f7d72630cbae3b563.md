## Direct transport and permit continuity

The existing independent direct-transport attacks still refuse forged
process-local authorization/permit state and reject the removed
caller-supplied source hash before fake-backend open. No caller-supplied
handoff-valid or manifest-valid boolean is accepted by the transport API.

The prior nonce defect remains in the supervisor-authorized route. I simulated
the supervisor's completed authorization consume and kernel capability at the
endpoint boundary, then used only the existing fake FTDI backend. The endpoint
issued permit P0; transport reconstructed P1 with a distinct nonce. Transport
opened and closed the fake backend once, then endpoint validation rejected the
observation at `LOCAL_VALIDATION / LOCAL_VALIDATION_FAILED` because it was
bound to P1 rather than P0. The authorization had already been consumed by
the supervisor. The reproduction is
`tests/reference/fk0957_endpoint_permit_reconstruction_attack.py`.

Without a supervisor capability, the route refuses at the authorization gate
before consuming authorization or reaching the backend. Thus the nonce bug is
not bypassed; it is still present when the intended authorized route is
simulated.

## Receipt, process, and supervisor findings

The independent cleanup attack suite ran 50,000 deterministic malformed/state
cases (seed `0x09572026`). It reproduced the required unsafe case:

- a forged terminal receipt named an actually absent PID;
- mocked process-start inspection returned `None`, while `/proc/<pid>` was
  absent;
- caller supplied `launch_closed=True`;
- receipt status became `CONFIRMED_EXITED_SUCCESS`, which is restorable.

The same suite still demonstrates caller-forged terminal receipt acceptance,
caller-controlled `launch_closed` yielding restorable `CONFIRMED_NOT_STARTED`,
and receipt destination/parent/terminal-state replacement races. SSH return
255 remains non-restorable `TRANSPORT_FAILED`; live PID inspection failure and
PID/start-identity mismatch refuse.

The new supervisor source avoids caller lifecycle fields, uses a root-owned
append-only state journal, and derives terminal status after `Popen.wait()` and
process-group checks. Its direct Python invocation returns 126 as non-root.
However, `install_fk0957_supervisor.py --verify` reports all deployment paths
missing; `--apply` deliberately refuses installation. The protected
supervisor boundary is therefore not provisioned in this environment. Legacy
receipt code remains directly forgeable as described above. Supervisor trust
boundary is not accepted as closed until an independently reviewable deployed
configuration and route prove the root-owned service is the only active
authority.
