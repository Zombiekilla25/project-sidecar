# FK0957 independent hardening audit: `57ff20b93a93b186c7b3dc7467772f663c587cd4`

This stable SHA adds a remote receipt writer/status helper. The helper is not
imported by the endpoint and is not invoked by RGB after SSH loss. The
handoff correctly states that it is not yet a deployed cleanup solution.

## Independent checks

- Watcher suites passed: 28 valid and 249,572 invalid oracle states with zero
  mismatches; 1,015 additional cases and 52 focused model tests. Acceptance,
  campaign, native-runtime and diff checks passed.
- Focused writer/orchestrator/endpoint tests: 31 passed.
- Scan transactions remain byte-identical to reviewed golden values:
  591/586/1177 TCK, Scan A SHA256
  `81f0fb9eefad365e50d8cdbe855274bdf408104158ac193a50798e0aaba778f2`, Scan B
  SHA256 `08534f71229a30798c82cc7518a934ada0113d38ba351ddb577ddd02a845336a`.
- The previous SSH-255 classification is corrected: rc 255 plus a refusal
  record yields UNKNOWN; rc 2 yields confirmed remote command exit.
- A 50,000-case deterministic malformed/replay/stale status campaign (seed
  `0x09572026`) returned UNKNOWN for every mutated record and produced no
  restorable state. Existing 231 receipt-type, 165 status-type, and 231 nested
  receipt-type tests also ran; `validate_status()` remained fail-closed.
- **New cleanup correctness defect:** `process_start_identity()` returns
  `None` for both absent `/proc` entries and read/parse errors. The receipt
  writer treats `None` plus caller-supplied `launch_closed=True` as an exited
  terminal process. With a receipt naming the current live PID, injecting an
  inaccessible `/proc/<pid>/stat` result yielded `EXITED_SUCCESS`, and
  `restore_allowed()` returned true while `/proc/<pid>` still existed. Exit
  proof must distinguish ENOENT from permission/read/parse failure and keep
  failures UNKNOWN.
- **Receipt path race:** injected replacement of `receipt.json` immediately
  after the final pre-rename identity/content check was not detected; the
  transition overwrote the competing replacement and returned success. The
  receipt directory is private but writable by the same acquisition UID, and
  the handoff explicitly says that same-UID processes can forge receipts. This
  helper does not yet provide a protected supervisor boundary against that
  threat. A second injection replaced a RUNNING receipt with a conflicting
  terminal refusal record bound to a different release authorization at the
  final rename boundary; the transition overwrote it with EXITED_SUCCESS and
  retained no detectable conflict. Thus the race can exchange terminal state
  as well as initial/claimed receipt identity. Fault injection before the temp-file fsync left the prior PREPARED
  receipt intact. An injected exception immediately after rename left the
  receipt advanced to CLAIMED; status remained nonrestorable UNKNOWN, which is
  the safe recovery behavior for that ambiguous caller outcome.
- Direct malformed calls to `validate_receipt()` still leak `TypeError` for
  unhashable state values; `validate_status()` catches those and returns
  UNKNOWN. `restore_allowed([])` and malformed direct transition helper calls
  likewise raise `TypeError`.
- Existing unrelated blockers remain: startup sentinels execute before trust
  validation; unregistered internal permit helpers can call transport; the
  local signer accepts a minimal fabricated record using a disposable test
  key; handoff authority/issuer provisioning is incomplete; and the offline
  topology guide still says the transport hash is null despite the reviewed
  adapter/hash existing.

## Verdict

The SSH-255 defect is closed in the inherited RGB orchestrator. The broader
remote cleanup proof remains **OPEN**: this helper is not wired into the live
path, its absence/error ambiguity can falsely permit restoration under the
stated caller contract, and there is no protected issuer/supervisor/status
service. No hardware, SSH, USB, or JTAG access occurred.
