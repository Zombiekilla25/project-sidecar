## Authorization change and bypass

The commit changes `_authorize_remote_permit` to revalidate a signed request and consume its authorization instead of accepting arbitrary digest arguments. Calling the helper with invented digest keywords now refuses.

However, the permit authorization registry remains a mutable module global, `_REMOTE_AUTHORIZED_PERMITS`. The ordinary Python import route can issue a permit from signed descriptor evidence, directly insert arbitrary digest values under `permit._token`, and call the public `run_fk0957_topology_discovery(permit)`. I reproduced this with the candidate’s fake backend: `fake_backend_open_count=1`, `permit_consumed=true`, `hardware_backend_used=false`. The physical-open boundary was exercised only in the fake transport. Thus signed release authorization can still be bypassed through direct internal transport invocation.

The candidate tests themselves use the same map-insertion seam to reach the public transport runner. No separate nonforgeable supervisor authority protects it. The release issuer pin is not provisioned in production, so the ordinary endpoint route remains unavailable; that does not close the direct internal path.

## Verdict

The signed-request change closes the prior arbitrary-digest argument route, but **does not close release authorization** because the mutable in-process registry can be written directly. `CALLER_CAN_FORGE_TERMINAL_STATE=YES`, `RECEIPT_REPLACEMENT_RACE=OPEN`, and `SUPERVISOR_TRUST_BOUNDARY=OPEN`. This is not a complete hardening candidate and is not ready for a live topology read.
